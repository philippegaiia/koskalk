## Plan written: Production Bench navigation hierarchy (plan only, no code)

Owner asked for a plan (not implementation) to fix the flat Production Bench nav. Chose the
"group the model" option: declare a real 3-tier tree, keep every existing `active`/`subnavigation`
prop so the 27 Livewire views need zero edits.

Plan: `docs/superpowers/plans/2026-08-29-production-bench-navigation-hierarchy.md`

Structure discovered (this is the part worth remembering):
- Two nav tiers today: `components/production-bench/navigation.blade.php` (8 flat underline tabs)
  plus three separate section components (inventory / purchasing / production-settings) that render
  as detached chip rows, selected by an `if/elseif` chain in `page.blade.php`.
- `Tasks`, `Flash planner`, `Calendar` are `production-bench.production.*` routes but are rendered as
  peers of Inventory and Purchasing; `Production setup` sits detached at the far right. That is the
  "flatness".
- Proposed tree: Home | Inventory(3) | Production(5, one of which is Setup with 7 grandchildren) |
  Purchasing(5). Level-1 row drops 8 items → 4, which is what makes it fit `--container-app: 74rem`.
- Key trick: node **keys** are chosen to equal the `active`/`subnavigation` values views already
  pass, so resolution is a lookup and no view changes.

Test constraints found (would bite any redesign):
- `tests/Feature/ProductionBenchLayoutTest.php` asserts exact `aria-current="page"` **counts** and
  the literal class strings `border-[var(--color-accent)] text-[var(--color-ink-strong)]` and
  `bg-[var(--color-accent-soft)] text-[var(--color-accent-strong)]`; it also forbids
  `overflow-x-auto` and `-mb-px` in `navigation.blade.php` and greps all 27 views for props.
- `tests/Feature/ProductionBenchProductionSettingsTest.php:196` asserts
  `Lang::get('production_bench.navigation.production', [], 'en') === 'Production setup'` — that key
  and value must survive. Several other labels are pinned by `assertSee`.
- `production_bench.*` keys live only in `lang/en/production_bench.php`; they are **not** in
  `database/seeders/data/interface-translations.json`, so no translation-seed sync is needed. Other
  locales have no `production_bench.php` and fall back to English.

House conventions to reuse:
- Nav CSS belongs in `resources/css/app.css` `@layer components` as `sk-*` classes with `.is-active`
  (precedent: `.sk-workbench-tabs` / `.sk-workbench-tab.is-active`), not inline Tailwind strings.
- Production Bench is the app's **first** multi-level nav — no precedent to mirror, so name classes
  generically (`.sk-nav-*`) for reuse by Settings/Account later.

2. **Production setup promoted from a Production child to a top-level tab, relabelled "Settings".**
   Reasons: users cannot see settings exist; a Production-named tab cannot host inventory/purchasing
   settings. This collapsed the nav from 3 levels to 2 — level 3 CSS is now dormant.
   - Node **key** stays `production-setup` (invisible to users; renaming it means editing 6 Livewire
     views plus the layout test's view scanner). Only the *label* changes.
   - Settings sits **right-aligned** (`ml-auto`) behind a divider — a utility, not a workflow step.
   - Its 7 children are grouped inside the rail under eyebrow sub-headings: **Production**
     (Numbering, Batch sizes, Task types, Task sets, Working calendar) and **Resources**
     (Departments, Employees). Adding an Inventory or Purchasing group is then a one-line config
     change. Sub-headings are *not* a third indent level.
   - Relabelling requires updating `ProductionBenchProductionSettingsTest.php:196`, which asserts
     `navigation.production === 'Production setup'`.

**Latent key collision found (worth remembering):** `calendar` is needed by two nodes — Production's
"Production calendar" and Settings' "Working calendar". `SettingsIndex::mount()` derives `$section`
from `request()->routeIs()` and `settings-index.blade.php` passes it straight through as
`subnavigation`, so the settings child key really is the bare string `calendar`.

> **CORRECTED 2026-08-29 (implementation).** I first claimed renaming `mount()` to emit
> `'working-calendar'` was safe because "`$section` is only ever compared against `'all'` in the
> view". **That was wrong.** `settings-index.blade.php:145` also does
> `in_array($section, ['all', 'calendar'], true)` to decide whether to render the working-calendar
> block, so the rename silently hid the section and broke
> `ProductionBenchProductionSettingsTest::organizes production setup into focused submenu routes`.
> Lesson: **`$section` in `SettingsIndex` is overloaded — it drives both the subnavigation and the
> content filter. It must keep matching the tree's node keys verbatim.** The fix was reversed: keep
> `mount()` on `'calendar'` and key the tree node `calendar`. No collision actually exists either —
> see below.

## Translation sync + catalogue import — done (owner approved)

### The blocker, and why my earlier recommendation was wrong

I had written "the DB is behind; run `translations:sync` then `translations:catalogue:import
--mode=authoritative`". Two things were wrong about that:

1. **The import was impossible, not just unwise.** `InterfaceTranslationCatalogue::read()` validates
   the *whole* catalogue and throws **before any DB write**. With the 7 stale
   `ingredients` / `validation.translation_write_intent_*` rows present, the command cannot run at all.
2. **`sync` and `import` are not the same class of operation.** `translations:sync` reads `lang/en`
   only (it never touches the catalogue), so it *was* runnable — but it only creates empty `text` rows,
   so it would not have landed the relabel. Worse, running sync-then-import would have inserted 58
   empty rows and then failed, leaving blank translations.

**Lesson: measure the blast radius before recommending a mutating command, and check whether the
command can even run — don't reason about it from the description.**

### What was run (with numbers measured first)

Dry comparison (catalogue vs. DB, no writes): 58 rows to create, **18** to overwrite
(17 `production_bench`, 1 `packaging`), 1 DB-only row that neither command deletes.

- `php artisan translations:sync` → 51 created, 2681 already present, 0 pruned
- `php artisan translations:catalogue:import --mode=authoritative` → 0 created, **69 updated**,
  2663 unchanged, 0 production values preserved

69 = the 51 empty rows `sync` had just created + the 18 predicted overwrites. Consistent.

### Catalogue change vs. HEAD is now +4 / −8

Added: `production_bench.navigation.{home_aria, production_runs, settings, settings_group_resources}`.
Removed: `production_bench.navigation.production` (renamed) and the 7 stale `ingredients` rows.
The correct `ingredients` / `editor.validation.translation_write_intent_*` rows already existed, so
deleting the stale ones was a pure deletion with no data loss.
