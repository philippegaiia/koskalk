# 2026-08-30

## Production bench: navigation + tables go from border to shadow (override O6)

Owner verdict after the O5 alignment fix landed: no border around the navigation or the tables,
give them the shadow everything else has, using `/ingredients` as the reference.

That reference is `.sk-card` — panel fill, `0.875rem` radius, a shadow, and **no border**. The
production bench table shells were `rounded-2xl border border-[var(--color-line)]
bg-[var(--color-panel)]`: a card drawn the wrong way round.

- `.sk-nav-rail` dropped `border`, `border-inline-start-width: 2px` and the four asymmetric radii
  that existed only to make that 2px edge meet the corners. Now `border-radius: 0.875rem` +
  `box-shadow: var(--shadow-card)`.
- All 11 table shells under `resources/views/livewire/production-bench/` now carry
  `overflow-hidden sk-card`; the stray `shadow-sm` on two of them went with them. Internal
  `border-b` / `border-t` / `divide-y` dividers are untouched — the border was only wrong on the
  *outer* box.
- New `--shadow-card` token in the `soapkraft.css` `@theme` block, read by `.sk-card`,
  `.sk-nav-rail` and the generated `shadow-card` utility.

Documented as **O6** in
`docs/superpowers/plans/2026-08-29-production-bench-navigation-hierarchy.md`.

**Retracted:** the O5-era suggestion to symmetrise the rail's `padding-inline: 1.125rem 0.75rem`.
With the 2px start border gone, that 0.375rem start excess is no longer incidental — it is what
sets the level-2 tabs inboard of the level-1 tabs, i.e. the nesting signal the border used to
carry. Do not "fix" it into symmetry.

## Three colour tokens that were used but never defined

Chasing why the tables still looked wrong after the border went: the table heads set
`bg-[var(--color-panel-muted)]`, and that token **has never existed** — not in any stylesheet, not
in any commit, anywhere in the repo including all worktrees.

| Token | Uses | Effect while undefined |
| --- | --- | --- |
| `--color-panel-muted` | 36 | backgrounds → transparent |
| `--color-ink-muted` | 47 | `color` inherits, so help text / captions / locked-input labels rendered at full body darkness |
| `--color-surface-muted` | 4 | production detail table head + group rows → transparent |

All three now defined in `soapkraft.css` (`--color-surface-muted` aliases `--color-panel-muted`).

**Worth remembering:** `color` is an inherited property, so an undefined colour token does not
vanish — it silently inherits. That is why 47 elements looked merely "too dark" rather than
obviously broken. Backgrounds go transparent; text goes *darker*.

No build step catches this: Tailwind emits `var(--x)` verbatim and Vite does not resolve custom
properties. New guard test
`ProductionBenchLayoutTest::defines every colour token the production bench views reference`
reads every `var(--color-*)` in the production bench views and asserts each is defined in one of
the four stylesheets. It found two of the three on its first run.

Owner chose: define both remaining tokens (rather than leaving them as known defects), and leave
the flash planner's line cards bordered (they are cards, not tables — keep the diff to the ask).
