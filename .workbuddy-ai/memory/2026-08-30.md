## Three colour tokens that were used but never defined

Chasing why the tables still looked wrong after the border went: the table heads set
`bg-[var(--color-panel-muted)]`, and that token **has never existed** — not in any stylesheet, not
in any commit, anywhere in the repo including all worktrees.

| Token | Uses | Effect while undefined |
| --- | --- | --- |
| `--color-panel-muted` | 36 | backgrounds → transparent |
| `--color-ink-muted` | 47 | `color` inherits, so help text / captions / locked-input labels rendered at full body darkness |
| `--color-surface-muted` | 4 | production detail table head + group rows → transparent |

All three now defined in `soapkraft.css` (`--color-surface-muted` aliases `--color-panel-muted`).

**Worth remembering:** `color` is an inherited property, so an undefined colour token does not
vanish — it silently inherits. That is why 47 elements looked merely "too dark" rather than
obviously broken. Backgrounds go transparent; text goes *darker*.

No build step catches this: Tailwind emits `var(--x)` verbatim and Vite does not resolve custom
properties. New guard test
`ProductionBenchLayoutTest::defines every colour token the production bench views reference`
reads every `var(--color-*)` in the production bench views and asserts each is defined in one of
the four stylesheets. It found two of the three on its first run.

Owner chose: define both remaining tokens (rather than leaving them as known defects), and leave
the flash planner's line cards bordered (they are cards, not tables — keep the diff to the ask).

## Code review — production bench inventory UX (branch `codex/production-bench-inventory-ux`)

Reviewed `2526eaa4..HEAD` (4 commits, 27 files) against the plan and the design spec.
Report: `.workbuddy-ai/reports/2026-08-30-production-bench-inventory-ux-review.md`.
Verdict: **not ready to merge** — 1 P1 data-integrity defect.

### Findings worth keeping

- **Buffer unit bug (P1).** `InventoryMaterialDetail` loads canonical grams into a field
  labelled with the workspace *display* unit, and saves the typed value unconverted.
  In a kg workspace, 1200 g shows as "1200.000000000" beside "(kg)" while the status line
  above correctly reads "1.20 kg"; typing "1.2" stores 1.2 **grams**. 1000x error, both
  directions. Every other quantity on the page converts via `formatQuantity()`/`MassConverter`
  — the buffer field is the lone exception.
- **Spec vs plan conflict on buffer units.** Spec line 197 says buffer is "expressed in the
  subject's canonical stock unit"; plan Task 6 Step 6 requires `MassConverter` conversion.
  Owner ruled: **follow the plan** (spec line 197 is about *storage*, per line 107's
  "Store ... in canonical units"). Spec wording still needs reconciling.
- **Missing `#[Locked]` is real but NOT remotely exploitable.** Livewire HMACs the whole
  snapshot with APP_KEY (`Checksum::generate()` covers `data`), so tampering throws
  `CorruptComponentPayloadException`. With a *recomputed* HMAC the subject IS redirectable
  (landed on an untracked ingredient), but cross-workspace is still refused by
  `SaveMaterialBuffer::assertSubjectAccessible()`. Defence-in-depth gap, not a live vuln.
  Sub-gap: `assertSubjectAccessible()` omits the `tracks()` check `resolveSubject()` applies.
- **N+1 in `WorkspaceMaterialInventoryQuery::hydrateRow()`**: 4.1 queries/row
  (102 @25/page, ~400 @100/page). Two per-row eager loads (`aliases`, `identifiers`) are
  never read — `localizedDisplayName()` only uses `translations`. Batchable to ~5 queries.
- **The plan-mandated `DB::enableQueryLog()` bounded-count test was never written** — which is
  exactly why the N+1 shipped. Add the test before the fix.
- `buffer_quantity` is NOT NULL but spec line 109 says nullable; v1 works only because
  `synchronize()` deletes the row, which blocks the reuse the spec anticipates.

### Environment gotcha (recurring)

A **worktree has no `.env`**, so every test warns `file_get_contents(.env)` from
`tests/TestCase.php:13`. Adding a gitignored `.env` (sqlite `:memory:`, as `phpunit.xml`
already forces) restores a clean run. Tests otherwise pass but are drowned in warnings.
Do not mistake those warnings for code defects.

### Review technique that paid off

`Livewire\Livewire::test()->set()` does **not** faithfully simulate a tampered HTTP request —
it showed the tamper as a no-op. The faithful path is to GET the page, regex the
`wire:snapshot`, tamper `data.subject[1].key`, and call
`app(HandleComponents::class)->update($snapshot, $updates, $calls)` directly. Always run an
**untampered positive control** first: my HTTP-body replay 404'd on everything, control
included, and would otherwise have been misread as "tampering is blocked".

## Step 3 (category/subcategory → Filament Selects): re-assessed, cost dropped a lot

Versions in the worktree: livewire/livewire v4.4.2, filament/forms + filament/schemas v5.7.6,
Laravel 13.29. Read the docs, not just vendor — the docs changed the plan.

- **Skip the plan's `filters.*` array.** Plan Task 4 Step 3 sketches `queryString()` with dotted
  keys (`'filters.category'`). Probed: it works on 4.4.2, but it is UNDOCUMENTED (Livewire 4 `url`
  / `attribute-url` pages show `#[Url]` and `queryString()` only on flat properties). Don't build a
  shareable-URL feature on an implementation detail.
- **Use Filament's documented "saving form data to individual properties"**
  (filamentphp.com/docs/5.x/components/form): omit `statePath()` and give each field its own public
  property. Selects then bind to the existing flat `#[Url]` props — no property moves, no new
  `queryString()`, aliases preserved.
- **`HasForms`/`InteractsWithForms` are thin shims** in v5: `HasForms extends HasSchemas` (empty
  body) and `InteractsWithForms` uses `InteractsWithSchemas`. Docs name HasSchemas/
  InteractsWithSchemas. Codebase + `.ai/rules/forms.md:9` use the shim consistently — naming drift,
  not a defect.
- **Filament Select writes `null` for "no selection"** (probe: `TypeError` "Cannot assign null to
  property ... of type string" from `data_set()`). Any flat property backing a Select MUST be
  nullable, or merely clearing the control 500s.
- **Livewire omits a URL param when `JSON.stringify(value) === JSON.stringify(except)`**
  (`livewire.js:14321`) — strict JSON compare. So turning a property nullable REQUIRES changing
  `except: ''` → `except: null`, else every cleared filter emits `?category=` into shared URLs.
  `except` is forwarded verbatim in the `url` effect (probed).
- **Present-but-empty param yields `''`, not `null`, even on `?string`** — contrary to the documented
  nullable behaviour. `BaseUrl` only substitutes null when the param is ABSENT; `data_get` returns
  `''` for `?category=`. Fold `''` → `null` in `normalizeFilterState()`; use `filled()` elsewhere.
- `->searchable()` forces the non-native JS select (`Select.php:1838`:

### Hardening the disagreements (owner is passing them to Codex)

Re-measured before hand-off. Two defences got materially stronger:

- **`app()` is not a standards violation.** Read the rule verbatim (`.ai/rules/services.md:15`):
  "Resolve them from the container (method injection into Livewire/controllers, constructor
  injection into Actions) — **never instantiate with `new`**." The prohibition is on `new`;
  `app()` IS container resolution, which the sentence affirmatively requires. The parenthetical is a
  preference, not an exclusive mechanism. Also: `InventoryMaterialDetail` DOES method-inject four
  services into `render()`; the 6 `app()` calls are in Filament `->visible()` closures and private
  helpers. And `boot()` is used by only **6 of 39** Livewire files while `app()` is used by **15 of
  39** (52 calls; `RecipeWorkbench` 12, `IngredientEditor` 9). The sibling `InventoryIndex` held up
  as the counterexample has `app()->getLocale()` at :850 — a locale read, not service location.
  (Corrected my own earlier numbers: IngredientEditor is 9, not 6.)

- **The "unbounded aggregation" fix is forbidden by the plan.** The obvious remedy — push grouping
  into `SUM(CASE …)` — violates plan line 829 ("never cast quantities to float"). Measured: SQLite
  `SUM()` on `decimal(20,9)` returns `typeof` = `real`; `123456789.123456789 + 0.000000001 +
  0.000000001` → `123456789.12345679` vs exact `123456789.123456791` = 1e-9 drift. PG's
  `SUM(numeric)` is exact but the suite/dev run SQLite. So the row-by-row `bcadd` accumulator is a
