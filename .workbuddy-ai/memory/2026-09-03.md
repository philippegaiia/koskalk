### getColor() → renderable badge families (measured)

`getColor()` returns 9 Filament *names* but the token palette only renders **5 distinct
hues** — success/emerald both green, info/blue/primary all blue, teal has no token.
So map, don't copy:

| getColor names | family | tokens | contrast |
|---|---|---|---|
| success, emerald | Botanical | success-soft / success-strong | 15.4:1 |
| info, blue, teal, primary | Functional | info-soft / info-strong | 14.1:1 |
| warning | Fragrance | see below | 8.4:1 |
| danger | Handle with care | danger-soft / danger-strong | 9.4:1 |
| gray | Inert | panel-strong / ink-soft | 11.3:1 |

All pass WCAG AA for 12px text (need 4.5:1).

**Two token traps found:**
- `--color-warning-soft` is hue 78 / chroma 0.029; `--color-panel-strong` is hue 84 /
  chroma 0.020. Only **6 degrees apart** — an amber badge built on `warning-soft` looks
  like the current grey one. Use `color-mix(in oklab, var(--color-warning) 20%,
  var(--color-panel))` instead → hue 54, chroma 0.033, **30 degrees** off neutral, 8.4:1.
- `danger-strong` is already used by the delete icon and the usage-count chip in this same
  table, so a red *category* badge shares a hue with destructive actions. Separate by
  shape (filled pill vs bare icon), not hue.

**Implementation constraint:** `getColor()` implements Filament's `HasColor` and must keep
returning Filament names for Filament components. Add a separate method (e.g.
`badgeTone()`); do not repurpose `getColor()`.

### Reusable technique

Built a static HTML replica of the Blade table with the real tokens from
`resources/css/shared/soapkraft.css`, then measured with headless Chrome:

```
/Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome --headless=new --disable-gpu \
  --no-sandbox --host-resolver-rules="MAP * 127.0.0.1" --window-size=W,H \
  --virtual-time-budget=6000 --dump-dom "file:///path.html" | grep -A1 'id="MEASURE"'
```

## INCI sentence case — `5e57c138`, `64390d8a`

Owner asked for the INCI under the name to be "small cap with only the first letter in
cap (not capitalize)". The real problem turned out to be that **stored INCI is
inconsistent**, not that it was too shouty: 110 distinct values in PG mix all-caps
(`ARGANIA SPINOSA KERNEL OIL`), title case (`Oenothera Biennis (Evening Primrose) Oil`)
and already-lower forms (`Adansonia digitata seed oil`). 43 of 110 change.

`InciName::display()` folds to sentence case with two protections:
- **Parentheticals are left alone.** `.ai/rules/ingredient-enrichment.md:65` defines the
  parenthetical as the botanical/common *proper* name (`Coconut (Cocos Nucifera) Oil`),
  so `(Kukui)` must not become `(kukui)`.
- **Identifier tokens are left alone.** A digit anywhere marks the token (`CI 77007`,
  `PEG-40`, `R102`); an all-caps word only counts as an acronym if it is on a known list,
  so `Tea` in `Black Tea Extract` still folds while `TEA` stays triethanolamine.

`InciName::normalize()` is **untouched** — it is the uppercase comparison key behind
catalogue dedupe (IngredientCatalogAuditService, CosIngFunctionDataset) and CosIng/FDA
matching. Never render it. A test pins the two apart.

Applied via `Ingredient::displayInciName()` in the index only. The other ~11 surfaces
render INCI client-side through Alpine (`x-text="row.inci_name"`), so a PHP formatter
cannot reach them — extending this means passing formatted values, not another helper.

### Answered: why not one colour per category

The token palette only yields ~5 genuinely distinct chromatic families — green (166),
blue (230), amber (49), red (25), olive (92). Everything else is a near-duplicate:
`accent` (55) is 6° from `warning` (49), `active` (146) and `sage` (148) sit inside the
green family, `quality-high` (38) falls between amber and red. 22 categories would need
16 invented tokens. Beyond that, categorical colour stops being learnable past ~5-8, and
red/amber already mean *delete* and *warning* in this UI. **The real defect is that
`functional` carries 8 of 22 categories** — the grouping is too coarse, not too narrow.

### Rejected: removing `whitespace-nowrap` from the category badge

Hypothesis: it raises the table's min-content floor and forces scroll. Tested — it does
lower min-content (DE 888 → 830, EN 844 → 812) but **loses on every other axis**:

- German badges go **two lines at 1280 *and* 1366**, i.e. even with 185px of slack,
  because once wrapping is allowed the Category column stops claiming width and the Name
  column eats it (catCol 197 → 160).
- At 1152 it still scrolls in English (−11), so it does not buy a lower floor either.

**`whitespace-nowrap` is the better choice**: it forces the column to take the width the
badge needs (catCol 197), keeps every badge on one line, and the table still fits at 1280
with 56–100px to spare. No code change made.

**Lesson:** a lower min-content is not automatically better. With `table-layout: auto`,
nowrap *wins* the column-width negotiation; wrapping concedes it to a greedier column.
- **Row heights with real names at 1280: 22 of 25 rows at the 72px target.** Only the
  two longest names (`Bergamot essential oil bergaptene free`, 38 chars) wrap to
  nameH=42 → 85px. At 1152 that degrades to a spread of 72/80/85/101.

### Why real names barely moved min-content

The Name column is floored at `min-w-48` (192px → 224px rendered), so min-content is
**insensitive to name length** there. Real data did not change the width verdict; it
changed the *row-height* verdict and it exposed the badge-label width risk, which no
factory fixture could have surfaced. Worth remembering: **a `min-w-*` floor makes a
column measurement lie about its content.**

### Measurement gotcha

`avail` (wrapper `clientWidth`) came back 801 in one run and 816 in the next at the same
viewport — a 15px delta, exactly one scrollbar, from a flaky headless render that the
harness silently retried past. **Do not trust a single headless measurement.** The
harness's retry loop masked it as a real value. Re-ran with `documentElement.clientWidth`
+ `scrollWidth` alongside; 816 was the reproducible number.

## Per-category badge palette — owner flipped the colour decision

Owner said: "I want to change the colors for categories. we should use the 1 color per
main categories. Keep it logical." That supersedes the five-family grouping I had built
the day before — every category now has its own hue.

### Decision: derive the badge modifier from `$this->value`, not from `getColor()`

`getColor()` collapses categories into broad Filament buckets — five categories collapse
into `gray`, three into `danger`. A per-category scale cannot be derived from that
grouping without making one of the buckets actually monochromatic. So `badgeTone()` is
gone and replaced by `badgeVariant()` returning `$this->value`. The CSS class then reads
`sk-badge-<value>`. Consequence: a new enum case needs one matching `.sk-badge-<value>`
rule — without it the badge renders colourless, and the contract test catches that
(`tests/Unit/IngredientTaxonomyTest.php`).

`getColor()` keeps returning Filament palette names. The two methods are now
deliberately independent and the test asserts that on every shared bucket (the five
`gray` categories must each have a distinct `badgeVariant()`, ditto the three `danger`).

### The palette — 22 hues, 16° apart, chroma as a second signal

Script: `/tmp/ing-measure/palette.mjs` (additions: `import { writeFileSync } from 'node:fs'`,
groups emission by family, also writes `/tmp/ing-measure/palette.json` for downstream
tooling). The review sheet lives at `/tmp/ing-measure/badge-swatches.html` and was built
by `swatches.mjs`, which pulls badge rules straight out of the served bundle rather than
retyping them.

- **Hue order encodes family.** 16° around the wheel. Process chemistry wraps the wheel
  on purpose (10, 26, 346) because all three are corrosive. Oil phase runs 106–186,
  water 202–218, surface 234–250, texture/polymers 266–298.
- **Chroma encodes hazard.** Hazard groups (preservation, pH, aromatics, alkalis) get
  chroma 0.150 text / 0.038 bg — the most saturated treatment. `bases_blends_premixes`
  is muted (0.078 / 0.020) because a blend has no chemistry of its own. `other` is
  near-neutral (0.012 / 0.006).
- **Every text colour solved for ~6:1 against its own background.** Worst case is
  `functional_polymers` at 5.25:1; AA needs 4.5. All 22 pass, all 22 stay inside sRGB
  gamut. Closest cross-family pair is 0.0359 in Oklab — about 3–4 JND, acceptable
  because the label carries the primary identity and only one or two badges appear per
  row.
- **Small lightness offsets cycle `[0, -0.030, 0.030, -0.015, 0.015]`** so adjacent hue
  neighbours never land on the same L. Without this the chord between adjacent hues is
  only ~2C·sin(8°), which gets crushed at low chroma.

### Honest defect: ΔE between some cross-family neighbours is 3–4 JND

`lipids` (170) and `fatty_derivatives` (186) are 0.038 apart; `actives` (314) and
`colourants` (330) are 0.036 apart. Side-by-side they read as "very similar" rather than
"different". With ~1–2 badges visible per row and the label text dominating, this is
*fine in practice* but I should not pretend the family separation is perfect. ΔE under-
weights hue angle at low chroma; the hues *do* differ by 16° each and that's visible
once you know what to look for.

### Two tests, not one

The old test asserted every category's `badgeTone()` resolved to one of five families
and had a stylesheet rule. It is replaced by:

- **"every category has a distinct badge variant with a matching stylesheet rule"** —
  parses `.sk-badge-<x> { body }` from `app.css`, asserts the body contains both
  `background-color:` and `color:` (not just `color:` — a half-written rule would
  otherwise leave the badge at 1.1:1 against the panel), and asserts all 22 variants
  are unique.
- **"keeps badge variants independent of the filament colour grouping"** — pulls
  `getColor()` for all 22, groups by it, asserts the five `gray` and three `danger`
  buckets each contain five/three distinct variants. This is the test that stops someone
  "simplifying" the two back into one.
- **"maps every category to a filament palette name"** — pins all 22 cases. The premise
  of the old "derives tones from filament colour" test was exactly what changed.

### Layout is byte-identical

The old rules set `background` + `color`; the new set `background-color` + `color`. No
size, font, or padding change. The 1280-floor verdict from the previous re-measurement
still holds. No re-measurement needed.

## Owner challenge: aromatics should not be one category

Owner: "users are making a big difference between the essential oils and a chemical
fragrance." Investigated rather than answering from the palette. **The owner is right that
the distinction is real; the model already has it; the UI throws it away.**

### The distinction already exists — at subcategory level

`IngredientSubcategory::category()` maps five cases to `AromaticMaterials`:
`essential_oils`, `absolutes_resinoids`, `co2_extracts` (natural) vs `aroma_compounds`
(synthetic isolates — linalool, vanillin, limonene) and `fragrance_blends`. The natural /
synthetic split is fully modelled. 80 subcategory cases exist in total.

### The collapse was deliberate, August 2026

`docs/superpowers/plans/2026-08-08-ingredient-taxonomy-cosing-functions.md:75, 247-248`:
legacy `essential_oil => aromatic_materials` and `fragrance_oil => aromatic_materials`.
The category is literally named **"Essential oils & fragrance materials"** — it was
designed to hold both, with the distinction pushed down to subcategory. Same plan, line
87: "Lavender hydrosol: `Botanicals & extracts / Hydrosols`; it is not an essential oil."
So the boundary was thought about carefully.

### But the data does not exercise it, and the UI never shows it

Measured against the Herd/PostgreSQL catalogue (`koskalk_restore_20260722_023001`, 170
ingredients, read-only `artisan tinker`):

- `aromatic_materials` = **30 rows, all `essential_oils`**, all
  `requires_aromatic_compliance = true`.
- `absolutes_resinoids`, `co2_extracts`, `aroma_compounds`, `fragrance_blends` = **0 rows
  each**.
- Searched the whole catalogue for linalool, limonene, geraniol, citral, vanillin,
  eugenol, galaxolide, ionone, benzyl, musk, parfum, fragrance — **zero hits**. The one
  "coumarin" match is a substring of "furocoumarins" in an essential-oil name.
- Only 11 of 22 categories are populated at all; `lipids` alone is 111/170 (65%).

So the split is a **latent capability**, not a live one.

### `.sk-badge-inert` is LIVE code, not dead CSS — I got this wrong at first

Grepping the literal `sk-badge-inert` returned nothing outside its own definition, which looked
like leftover CSS from the superseded five-family design. **It is reachable.** The class is
built by concatenation:

```blade
ingredients-index.blade.php:162
<span class="sk-badge sk-badge-{{ $ingredient->category?->badgeVariant() ?? 'inert' }} …">
```

It is the **null-category fallback**, and `app.css:505-511` documents it as deliberate:
"Not a category: the fallback for an ingredient with none. It stays neutral rather than
claiming a hue, and it is intentionally close to `other`." It uses `--color-panel-strong` /
`--color-ink-soft` **tokens**, not generated `oklch()` — which is exactly why
`badge-palette.mjs --check` never touches it (that checks the 22 category rules only).

Reachability: **0 of 170** live ingredients have a null category, so it is unexercised by
current data. Still correct to keep — defensive, and no test would catch its deletion.

**Method lesson (repeat offender):** a literal grep for a CSS class that is *composed at
runtime* always returns nothing. Search the interpolation site (`?? 'inert'`,
`sk-badge-{{`), never the composed string. "No literal reference" ≠ "no reference".
