Owner: in the ingredients index, "when we enter a price it is aligned left and not aligned on

## The defect

`resources/views/livewire/dashboard/ingredients-index.blade.php:171-185`

```blade
<input value="{{ $this->formattedPrice($ingredient->user_price_per_kg) }}"
       wire:change="updateIngredientPrice({{ $ingredient->id }}, $event.target.value)"
       type="text" inputmode="decimal"
       class="sk-input numeric" … />
```

`.numeric` (`app.css:39-43`) only sets `font-family: var(--font-numeric)` +
`font-variant-numeric: tabular-nums` + `font-feature-settings: 'tnum'`. It does **no
alignment**. `.sk-input` (`app.css:213`) sets no `text-align` either. So the text is left
aligned and the decimal separator drifts with the length of the integer part.

`formattedPrice()` (`IngredientsIndex.php:429`) → `NumberLocale::formatDecimal($v, 2, $locale)`,
which is **always exactly 2 decimals and never groups thousands** (`number_format($v, 2, '.', '')`,
then `.` → `,` for fr_FR/es_ES/de_DE/it_IT/nl_NL/pt_BR). Fixed decimals are what *make*
decimal alignment possible — the separator is always 2 chars from the right.

Measured integer-digit spread for realistic prices (unit is **kg** metric / **lb** US customary
— `MassDisplaySystem::priceUnit()`; never g):

| value | en_US | fr_FR | intDigits |
|---|---|---|---|
| 0.05 | 0.05 | 0,05 | 1 |
| 5 | 5.00 | 5,00 | 1 |
| 12.5 | 12.50 | 12,50 | 2 |
| 125 | 125.00 | 125,00 | 3 |
| 12500 | 12500.00 | 12500,00 | 5 |

1–5 integer digits down a column → the separator wanders across ~4ch.

## The house pattern: `sk-decimal-aligned` (the "shared responsive decimal anchor")

This is what `.ai/rules/recipe-workbench.md:9` means by "the shared responsive decimal anchor
and locale separator". Three cooperating pieces:

**1. CSS** — `resources/css/app.css:572-580`, top level in `@layer components`, so it is
**globally available, not scoped to `.sk-workbench`**:

```css
.sk-decimal-aligned {
    --sk-decimal-offset: 1ch;
    width: 100%;
    justify-content: flex-start;
    padding-inline-start: max(0.75rem, calc(50% - var(--sk-decimal-offset)));
    padding-inline-end: 0.75rem;
    text-align: start;
}
```

It is **not** `text-align: right`. It left-aligns the text but pads the start so the decimal
separator lands on the **50% centre line**. `max(0.75rem, …)` clamps so long values can never
push the text past the left edge.

**2. JS offset** — `resources/js/recipe-workbench/sections/formula-section.js:736`:

```js
decimalAlignmentStyle(value) {
    const numericValue = this.number(value);
    const signCharacters = numericValue < 0 ? 1 : 0;
    const integerCharacters = Math.trunc(Math.abs(numericValue)).toString().length + signCharacters;
    return `--sk-decimal-offset: ${integerCharacters}ch`;
},
```

Applied as `:style="decimalAlignmentStyle(row.percentage)"`. The `ch` unit only works because
`.numeric` forces tabular figures — every digit is exactly as wide as "0". **`.numeric` is a
hard prerequisite, not decoration.**

**3. Re-format on state change** — `x-effect="syncFormattedInput($el, v, decimals)"`
(`formula-section.js:744`) rewrites `element.value` to the fixed-decimal form, bailing out when
the element is focused so it never fights the user mid-typing. Paired with
`@blur="normalizeDecimalBlur($event)"` (`costing-section.js:617`) which re-normalizes through
`formatDecimalInput` (0–12 decimals, no grouping) and dispatches a bubbling `input` event.

## Two formatter tiers — display vs input

| tier | JS | PHP | shape |
|---|---|---|---|
| display / readout | `formatNumber(v, n, locale)` | `NumberLocale::formatDecimal($v, n, $locale)` | fixed n decimals, **no grouping** |
| input | `formatDecimalInput(v, locale)` | `NumberLocale::formatAdaptiveDecimal($v, 2, 4, $locale)` | 0–12 decimals (JS) / trailing zeros trimmed (PHP), no grouping |

Both use `Intl.NumberFormat` with **`useGrouping: false`** — thousands separators are
deliberately absent everywhere, which is precisely what makes a fixed decimal anchor viable.

## Design notes for whenever this gets built

- **The price input is Blade/Livewire, not Alpine.** The workbench inputs get their offset
  reactively via `:style` + `x-effect`. Here the value is server-rendered, so the offset has to
  be computed in PHP (integer digit count of the already-formatted value) or the input converted
  to Alpine. Server-side is the smaller change and matches the rest of the index.
- **Cascade interaction to check:** `.sk-decimal-aligned` (line 572) and `.sk-input` (line 213)
  are both single-class in `@layer components`, so source order decides and the later rule's
  `padding-inline-*` longhands override `.sk-input`'s `padding: 0.75rem 1rem` shorthand.
  Verify the resulting padding rather than assuming.
- **Nothing is pinned by tests.** `grep` for `sk-decimal-aligned`, `decimalAlignmentStyle`,
  `formattedPrice`, `updateIngredientPrice` across `tests/` returns **zero files**. Low risk to
  change, but also nothing protects the behaviour.
- Empty case: `formattedPrice()` returns `null` for null/empty → the input renders blank; an
  offset computed from 0 gives `1ch`, which is harmless.
- Still open from before: the input has **no save state** (`wire:change` fires on blur with no
  feedback) — a separate UX issue from alignment.

## Why the workbench anchor exists — variable decimals, not aesthetics

The 50% `ch` anchor is **not** a stylistic choice; it is required by variable precision.
`massDisplayDecimals(value, unit, profile)` (`resources/js/recipe-workbench/mass.js:58`) returns
**0, 1, 2, 3 or 4** depending on unit, profile and magnitude (addition profile: 4 for kg/lb, 3
otherwise; calculated profile in g above 100: 0; g at ≥1000: 1; g otherwise 2…). With a varying
number of fraction digits, **right-aligning does not align the separator** — hence the offset.

The price field is different: `NumberLocale::formatDecimal($v, 2, $locale)` is **always exactly
2 decimals**. Fixed decimals mean the last two characters always occupy the same width under
tabular figures, so **`text-align: right` alone aligns the separator perfectly.** The anchor
would add centring, not correctness.

**General rule: a decimal anchor is only necessary when the fraction length varies.** Reach for
`text-right` first; it is what the project already does for numeric *readouts*
(`fatty-acid-profile.blade.php:25,60`).

### The JS helpers are NOT exported — reuse is not a free import

`decimalAlignmentStyle` and `syncFormattedInput` are methods inside the object literal returned
by `createFormulaSection()` (`formula-section.js:34-35`), not standalone exports. Reusing them
outside the workbench means either extracting them into a shared module (one implementation, two
consumers) or computing the offset elsewhere. `.sk-decimal-aligned` **is** genuinely reusable
as-is — top level in `@layer components`, not scoped to `.sk-workbench`.

## AUDIT: is the workbench decimal anchor necessary? — 36 of 40 sites say NO

Owner pushed back on my "the anchor is necessary because decimals vary" line. Audited all **40**
`sk-decimal-aligned` + `decimalAlignmentStyle()` call sites (7 Blade partials). Result: **only 4
genuinely need it.**

| group | sites | verdict |
|---|---:|---|
| literal `format(x, N)` | 30 | redundant — decimals fixed |
| `additionWeightDecimals` (post-reaction 64/67/139/142) | 4 | redundant — **no magnitude term**, 3 for g/oz, 4 for kg/lb |
| costing-tab inputs 109/181 | 2 | redundant — fixed 2 |
| `oilWeightDecimals` (reaction-core 127/130/153) | 3 | **NEEDED** — g: `>=1000 ? 1 : 2` |
| `formatPackagingQuantity` (costing-tab 170) | 1 | **NEEDED** — integer → 0 decimals, else 3 (**3-char drift**) |

**`oilUnit` is a single user-selectable scalar for the whole formula** (`changeOilUnit`,
`component.js:492-501`; init `payload.preferredMassUnit` else `'g'`, `component.js:159-161`) — it
is NOT auto-promoted g→kg as the batch grows. So the unit is constant down a column and only the
**magnitude thresholds** in `massDisplayDecimals` (`mass.js:58-90`) can vary the fraction length.
That is why a 1500 g batch in grams shows `1200.0` next to `50.00`.

**Root cause is not the alignment technique — it is that the decimal count varies row-by-row
within one column.** Make it uniform per column and the whole JS mechanism is deletable. But that
changes *displayed precision* (`1200.0`→`1200.00`, `4`→`4.000`), so it is a product decision.

### Padding-right that varies per value BREAKS the alignment

Separator x = `right edge − padding-right − (fraction × 1ch)`. So a per-row computed
`padding-right` moves the separator with the value — the exact bug just fixed. "Conditional"
padding is only safe when the condition is not the number itself (this-input-only, breakpoint…).

**`--font-numeric` is monospace** (`ui-monospace, SFMono-Regular, Menlo…`, `soapkraft.css:4`), so
`1ch` = one glyph advance exactly (≈8.4px at 14px) and `tabular-nums` is belt-and-braces. Widest
price `99999.99` = 8ch ≈ 67px vs an 80px content box (`min-w-28` 112px − 32px padding). Budget:
`pr-6` (24px) → 72px, fits; `pr-8` (32px) → 64px, **clips 5-digit prices**. Full centring is
unreachable at this width (needs ~39px padding → 57px box).

Plan written but NOT built — owner asked "plan only":
`docs/superpowers/plans/2026-09-04-decimal-alignment-consolidation.md`. Part 1 = `pr-6` on the

`@layer utilities`, layer order beats the padding shorthand). Part 2 = three options for the
