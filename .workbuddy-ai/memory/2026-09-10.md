# 2026-09-10

## Formula-sheet export audit (read-only, no code changed)

Asked what generates the workbench CSV/XLSX and whether the approach is proper.

- **XLSX** → `openspout/openspout` v4.32.0 in `app/Services/RecipeWorkbookExporter.php`.
- **CSV** → no library; native `fputcsv` in `app/Services/RecipeCsvExporter.php`.
- Routes `recipes.export.xlsx` / `recipes.export.csv` (`routes/web.php:100-101`), both `throttle:10,1`,
  handled by `RecipeController::exportSavedWorkbook` / `exportSavedFormulaCsv`.
- Nothing generated client-side — no csv/xlsx code anywhere under `resources/js`.

Findings (none fixed, all still open):

1. **`openspout/openspout` is a transitive dep.** `app/` imports `OpenSpout\*` directly but
   `composer.json` only gets it via `filament/actions`. Still worth promoting to a direct `require`
   on principle, but severity is low: `filament/filament` hard-requires `filament/actions` at
   `self.version`, so OpenSpout is guaranteed present while Filament is installed. A break would
   require Filament's actions package itself to drop OpenSpout.
2. **`close()` double-call is fine.** `AbstractWriter::close()` guards on `isWriterOpened`, so the
   nested `finally` blocks in `RecipeWorkbookExporter` are harmless. Checked, not a bug.
3. **Export isn't actually streamed.** Both exporters build the whole file in memory
   (`tempnam` + `file_get_contents` → string) before `streamDownload(fn () => print $string)`, so
   OpenSpout's row-streaming advantage is discarded. `print` returns `1` only to satisfy `: int`.
4. **CSV has no UTF-8 BOM.** `charset=UTF-8` header doesn't help Excel, which ignores it for local
   files. Non-ASCII ingredient names will mojibake on double-click. XLSX is unaffected.
5. **Column headers are English-only; sheet names are NOT (initial claim corrected).** Workbook sheet
   names go through `__('formula_documents.exports.*')` and those keys ARE translated into all 6
   non-English locales in `interface-translations.json` (`exports.ingredient_batch` → "Zutatenansatz"
   etc.) — so the `__()` calls work. What genuinely lacks translations is the column headers
   ("Section", "Percentage basis", …), hardcoded English in both exporters with no translation keys.
   `tests/Feature/RecipeVersionPagesTest.php:774` asserts the exact English header string, locking it in.
   Fix = add `formula_documents.exports.*` keys for the headers and route both exporters through them.
6. **CSV formula injection** — user-supplied ingredient names starting `= + - @` execute as formulas
   on open. Low severity (users export their own data), cheap to escape.

Test coverage is otherwise strong: 404 for other users, throttle middleware, per-version isolation,
and real XLSX validation by unzipping and reading `xl/worksheets/sheet1.xml`.

## Export strategy consultation (proposal, nothing implemented)

User deciding what to export per page. Verdict given: OpenSpout direct is right for export-only;
if they want a Laravel-idiomatic layer, `spatie/simple-excel` (wraps OpenSpout, streams properly,
one API for CSV+XLSX) beats `maatwebsite/excel` (PhpSpreadsheet, heavy; only worth it for rich
imports). Proposed decision rule: flat/interchange table → CSV; multi-section human document → XLSX;
one-pagers → existing print/PDF. Per-area proposal: ingredients index CSV (library interchange),
packaging index CSV, inventory stock CSV + material movements CSV, costing XLSX (completes the
formula-bench print set), supplier listings CSV (price comparison), receipts CSV (bookkeeping),
production run XLSX batch record (ISO 22716 GMP relevance), consolidated requirements shopping CSV.
Route convention: extend `*.export.csv` pattern; export-as-filtered; same ownership scoping +
throttle as recipe exports. Awaiting user pick before any code.

## Anti-siphoning design for ingredient export (user requirement, agreed)

User fears a fake user bulk-downloading the platform DB via export. Key finding:
`IngredientsIndex::ingredientQuery()` mixes user/workspace-owned rows (`applyCompanyIngredientScope`)
with the shared platform catalog (`owner_type IS NULL AND is_active`, the "soapkraft" filter).
Agreed design:

1. **Export = 'mine' scope only** — `applyCompanyIngredientScope($query, $user)`, never platform rows.
   Platform catalog never ships in bulk; formulas referencing platform ingredients keep working since
   formula exports already carry names.
2. **User-owned fields only** in the CSV (their names/INCI/identifiers/prices/notes) — it's a data
   backup, which is also the GDPR portability angle.
3. **Daily quota, not just throttle** — `throttle:10,1` limits rate, not volume; add a per-day
   export counter (RateLimiter with 86400 decay or cache counter).
4. **Optional entitlement gate** — `EntitlementService` already limits private ingredients per plan
   (`privateIngredientUsageFor`); bulk export can be a paid-plan feature. Business decision, user to decide.
5. Honest framing given to user: anything paginated in the UI is already scrapable; export adds
   convenience, not access — the real protection is scope (point 1), not secrecy.

## Export gating decisions (user, final)

- **All new exports gated to a higher paid plan** — "not the smaller paid plan". Formula exports
  (existing `export.xlsx`/`export.csv`) stay ungated. Mechanism: plans are DB rows (`Plan` +
  `PlanLimit` key/value, admin-editable, fallback to `is_default`; currently only `free-beta` is
  seeded — paid plans are created in admin). Add a boolean limit key `bulk_exports` (0/1);
  `EntitlementService::limitsFor()` already merges plan limits, so a `canExportData(User)` method
  reads `bulk_exports > 0`. Free-beta seeder gets `bulk_exports => 0` explicitly.
- **'mine'-only scope was wrong** (user correction): users overlay their own data on platform
  ingredients — workspace price (`currentPrices`, workspace-scoped) and own material code
  (`WorkspaceIngredientCode`, via `Workspace::ingredientCodes()`). Revised scope: user/workspace-owned
  rows export fully; platform rows export ONLY when the workspace has overlaid data (price or code)
  and then only identity name + the user's overlay fields — no platform enrichment (INCI schemes,
  CAS, functions). Catalog siphoning then requires a higher paid plan + manual annotation effort.
- Daily export quota on top of entitlement (paid users too), ~20/day.
- Gate response: 404 (consistent with app's hidden-resource pattern); UI hides export buttons for
  non-entitled users with upsell hint.
- Not yet implemented — user to green-light.

## User ingredient import (migration from other software — user idea, design agreed in principle)

Context: existing `IngredientIntake` (parser, batch, Filament resource, `ingredient_intake_admin` lang)
is the **admin** catalog pipeline feeding AI enrichment (see `.ai/rules/ingredient-enrichment.md`) —
NOT user-facing migration. User import is new but reuses its parser pattern (header aliases,
delimiter detection, SplFileObject).

Design points:

- **Library**: OpenSpout **Reader** is already installed (CSV + XLSX + ODS) — no new dependency for
  import either. `maatwebsite/excel`/PhpSpreadsheet only if legacy .xls support is ever required.
- **Flow**: upload → column-mapping screen (their software's headers ≠ ours) → preview with per-row
  match result → confirm → queued import job.
- **Match to platform catalog by INCI name + CAS/EC identifiers** (`IngredientIdentifierScheme`:
  cas, ec, unii, cosing_ref, …). Matched rows become workspace price/code overlays — do NOT consume
  `private_ingredients` quota. Unmatched rows become private ingredients — quota applies (free-beta
  = 20), so import must cap/stop at remaining limit with a clear message.
- **European CSV traps** (8-locale app): Excel-EU exports `;`-delimited CSV with comma decimals;
  encoding often Windows-1252, not UTF-8. Delimiter + decimal-separator + encoding detection all
  required or imports mojibake/misparse (mirror of the export BOM issue).
- **Input-side security**: file type/size validation, row cap, CSV formula-injection sanitization on
  import (crafted `=cmd` cells would re-export later), idempotent re-import (match user's own private
  ingredients by name/code → update, not duplicate).
- Not yet implemented — user deciding; likely next after export work.
