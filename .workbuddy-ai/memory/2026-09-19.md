## Enrichment "stale on apply" investigation (production report, no prod DB access)

Traced the stale rail end to end; conclusions worth keeping:

- Item fingerprint (`ingredient_enrichment_batch_items.source_fingerprint`) is captured at **request
  creation** (`IngredientEnrichmentBatchService::start`), re-checked at **approval**
  (`ApproveIngredientEnrichmentItem` hard equality on `snapshotBuilder->fingerprint($ingredient)`),
  and re-checked at **apply** (`ApplyPlatformIngredientEnrichment`, `ApplyIngredientGuidanceRefresh`).
  Because approval already enforces equality, an apply-time stale means the ingredient was written
  **after approval**, i.e. by an earlier item in the same apply loop (only possible when two items
  share one ingredient — intake rows both resolved to the same existing ingredient) or by a
  concurrent/other-tab writer (another enrichment or guidance request applied first, manual edit).
- Research itself never writes the ingredient (no `save()` in `IngredientEnrichmentPipeline`), so
  research is not the source.
- ~~Asymmetry: an item with no applicable changes returns `unchanged` even when the fingerprint
  moved.~~ **Wrong — corrected below.** In `ApplyPlatformIngredientEnrichment::applyLocked` the fast
  `unchanged` return also requires `currentFingerprint === storedResultFingerprint`, and the second
  `unchanged` return sits *after* the guard, so a moved fingerprint reports stale whether or not the
  item carries changes. The only path that skips the guard is `$promotion` (intake promotion).
- Recovery gap: `RetryIngredientEnrichmentFailures` only picks `failed`/`warning`, so **stale items
  cannot be retried** — the only path today is a new enrichment request.
- Diagnostic written: `.workbuddy-ai/artifacts/enrichment-stale-diff.php` (read-only; per item prints
  request-time vs current fingerprint, approved_at vs ingredient.updated_at, stored
  `enrichment.core.applied_at`, and a field-level diff of `snapshot['current']` vs now).
  Run: `php <script> <batch_id_or_public_id> <project_root>`. Validated locally against batch 83.

## Root cause confirmed by the owner

They manually edited the ingredients in that batch **between approval and apply**. That is the whole
story: approval passed because the edits came after it, then apply's second fingerprint check failed
on every ingredient they had touched. "Some, not all" is simply "they edited some" — the no-change
short-circuit I first blamed does **not** precede the guard (see the correction above). This also
confirms the guard did its job: nothing of theirs was overwritten.

## Third commit + review of the branch

- `b16b359a`: `refreshSnapshot()` was rebuilding guidance contexts with the default
  `$freshResearch = false`, so retrying a stale item in a `fresh_research` batch would have silently
  reused persisted evidence instead of re-gathering it. Threaded `(bool) $locked->fresh_research`
  through and asserted `snapshot['fresh_research']` in the guidance retry test.
- Wrote a pre-merge handoff for a reviewing agent at
  `.worktrees/enrichment-stale-apply/HANDOFF.md` (untracked; delete before merging).
- Reviewer verdict: **SAFE-TO-MERGE** with one required change, plus three falsification attempts
  that all failed to break "apply-time stale ⇒ a write landed after approval". It also corrected my
  handoff: `markAppliedWhenComplete` is at `IngredientEnrichmentBatchService.php:434` (not 218) and
  never reads `Stale`. Only consumer of the apply totals array is a notification string
  (`ViewIngredientEnrichmentBatch.php:28`).
- `ab1f6672` (the required change): non-fingerprint apply rejections now carry
  `failure_code = IngredientEnrichmentBatchItem::APPLY_REJECTED`, and `retryableFromStage()` returns
  null for a `Failed` item with that code. Before this, they were `Stale` (retry skipped them); after
  the earlier commits they became `Failed` (retry would re-run the whole pipeline and fail
  identically forever, because `owner_type`/`owner_id` are not in the snapshot).
- Verified after the fix: Pint PASS; 15 enrichment test files, 140 passed / 821 assertions.
