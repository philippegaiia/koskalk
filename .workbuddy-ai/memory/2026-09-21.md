## Repo visibility audit (planning only — nothing changed)

Owner asked what breaks if `philippegaiia/koskalk` goes from public to private. Plan-only
request; no files or settings touched. Audited the actual dependency surface rather than
reasoning generically. Findings worth keeping:

**Facts about the repo as of today** (via `gh` API, `/opt/homebrew/bin/gh` — not on the
sandbox shell's PATH, so call it by absolute path):

- PUBLIC, personal account, created 2026-03-23, default branch `main`.
- `forkCount: 0`, `stargazerCount: 0`, collaborators: owner only. No external audience,
  and no GitHub-side copies to worry about.
- **No `.github/` directory at all** → no Actions workflows, no Dependabot, no CodeQL.
- **No repo deploy keys** (`/keys` empty) and **no repo webhooks** (`/hooks` empty).
  So Forge is not wired via a site deploy key, and **push-to-deploy is not configured** —
  deploys are triggered manually. This is the single most useful fact: a visibility flip
  cannot silently break the deploy pipeline.
- **No branch protection on `main`** (404) and **no rulesets** (`[]`).
- No Pages site (404), 0 releases, wiki enabled, 13 remote branches (12 `codex/*` + `main`),
  5 issues total / 0 open.
- `licenseInfo: null` — no LICENSE file, though `composer.json` declares MIT.

**Secret audit across all 13 branches — clean.** Only `.env.example` was ever added; its
contents are all placeholders. Scanned `git log --all -p` for AKIA / sk_live / ghp_ / gho_ /
xox / AIza / pdl_live / PRIVATE KEY / credentialed DSN patterns. The only hits were
`postgres://user:secret@database.example/koskalk` in
`tests/Unit/TestDatabaseSafetyTest.php` — a deliberate fake DSN in a test, not a credential.
So there is nothing to rotate on account of this repo's history.

**Verified trade-offs of going private** (GitHub docs, checked this session):

- Rulesets/branch protection are "available in public repositories with GitHub Free … and
  in public and private repositories with GitHub Pro, GitHub Team, and GitHub Enterprise
  Cloud" → on Free, a private repo cannot have them. Nothing breaks today (none exist), but
  `main` deploys to production and would be unprotected.
- Push protection **for users** "stops you from pushing secrets to public repositories" and
  is enabled by default → it stops applying once the repo is private. Repository-level push
  protection "requires GitHub Secret Protection" (paid). Free mitigation: local
  `gitleaks`/`detect-secrets` pre-commit hook, since there is no CI to hang it on.

**Forge wiring (from laravel.com/forge/docs):** an OAuth source-control connection "grants
Forge access to all repositories accessible by your authenticated account"; if the site is a
**Custom** Git site instead, the server's account-level SSH key (`/home/forge/.ssh/id_rsa.pub`)
covers private repos too. Custom sites cannot use push-to-deploy. The site-level **deploy
key** is the recommended least-privilege option and works fine for private repos. The
action item if a private repo drops out of Forge's reach is Source control → *Manage GitHub
access*.

**Not verified:** which Forge connection mode this site actually uses (needs the Forge
dashboard), and whether the Forge GitHub app installation is scoped to all repos or a
selected list.

## Formula table: soap/cosmetic divergence closed (same session)

Follow-up on the one thing the density pass left open. Findings, all from the code:

- **`.sk-formula-table-cell` / `.sk-formula-table-handle-cell` declared `background: white` in
  `@layer components`, and every one of the 20 cells carrying those classes also carries a
  `bg-*` utility** → dead CSS, and misleading (it said "white" where cosmetic renders panel).
  Removed from both rules; guarded in the polish test. Verified the guard *fails* by
  re-adding the declaration (it does), then restored.
- **Row surface: I tried to unify cosmetic onto `bg-white` and had to revert it.** Reasoning was
  the majority convention — every other workbench table body is white (reaction-core,
  post-reaction ×2, costing ×2, packaging, output-tab ×2, ingredient-list tbody; output-tab
  serves both workbenches) — plus `DESIGN.md` calling panel a card colour. I changed 8 spots,
  and the full suite then failed `CosmeticRecipeWorkbenchTest:525`, which asserts
  `->not->toContain('bg-white')` on the rendered cosmetic partial. `git log -S` showed that
  guard landed in the *same* commit (`1ec5c59e`) that moved cosmetic rows to panel: it is a
  deliberate, protected decision, not drift. **Reverted all 8; cosmetic stays panel.** Lesson
  carried into the deep reference: a majority convention is not licence — grep for a
  `not->toContain` guard on the surface before "unifying" one.
- **`post-reaction`'s `flex flex-col justify-center` is correct, not drift** — no inspector
  popover there, so the two `<p>` sit directly in the cell. Left alone.
- Cascade layer order (`theme, base, components, utilities`) read from the compiled dev CSS, not
  assumed — and a substring scan for "which layer is this rule in" is unreliable: `.sk-formula-
  table-cell` also appears inside the compound `.sk-added-row-highlight` selector in the
  utilities block. Anchor the regex to a selector start (`(?:^|[},])\s*\.class\s*\{`, `/m`).

Net change this turn: only the two dead `background: white` declarations removed. Verified the
new guard fails when the declaration is re-added, then restored. Still uncommitted on
