# 2026-09-28

## Export & print UX — analysis only (no build)

Owner asked for a per-view brainstorm of export (CSV/XLSX) and print (PDF) actions across
the app, prioritised by usefulness, explicitly "not to overdo". Owner then said **no build**.

Deliverable: `docs/superpowers/plans/2026-09-28-export-and-print-actions-design.md`

Baseline facts established (verified, worth reusing):
- Export exists **only** for saved recipes (`recipes.export.xlsx` / `.csv`,
  `RecipeController::exportSavedWorkbook` / `exportSavedFormulaCsv`, services
  `RecipeCsvExporter`, `RecipeWorkbookExporter` via OpenSpout, `RecipeExportDataBuilder`).
- The **recipe workbench has no export and no print at all** — all artifacts live on the
  saved product sheet (`resources/views/recipes/version.blade.php`). Biggest gap: a
  formulator must publish before they can print a worksheet.
- **Costing is not exported at all** — existing exporter carries ingredient rows only.
- **Production Bench has zero export** of any kind.
- No PDF library; "PDF" = browser print-to-PDF. Keep it that way.
- Filament admin has `IngredientExporter` / `FattyAcidExporter`; the app UI does not.

**Latent bug found (not fixed):** the five print routes `print.recipe`, `print.production`,
`print.details`, `print.technical`, `print.costing` all funnel into
`RecipeController::printSheet`, which accepts `$printMode` and never passes it to the view
(`app/Http/Controllers/RecipeController.php:813-836`). All five render the identical
`recipes.print` page. Fix or collapse before adding new print affordances.

Conventions to match when this is built:
- Export: `App\Services\*Exporter` returning a string → `response()->streamDownload`,
  throttled `workspace-exports`.
- Print: standalone Blade view + `window.print()` via `data-print-document`,
  throttled `workspace-prints`. Limiters in `app/Providers/AppServiceProvider.php`.

Tier 1 list is in the design doc (10 items). Rule adopted for prioritisation: **print** =
artifact used away from the screen with a pen; **export** = data worked with elsewhere.
Views whose best artifact is neither get nothing.

### Follow-up: Tier 1 implementation plan

Owner said "continue" → wrote
`docs/superpowers/plans/2026-09-28-export-print-tier1-implementation.md` (15 tasks, TDD,
Pest, Pint). No code written.

Feasibility facts confirmed while planning (these made the plan much cheaper):
- `RecipeVersionCostPreviewBuilder::build(Recipe, RecipeVersion, User, $batchBasisValue,
  $unitsProduced)` already produces the full costing payload server-side (currency,
  ingredient_rows, packaging_rows, totals, cost_per_unit, has_unpriced_rows) **and already
  authorises** via `Gate::forUser($user)->authorize('view', $recipe)` (line 38-39). So
  costing export needs no new permission model — answered the open question.
- Costing context is persisted on `RecipeVersionCosting` (`oil_weight_for_costing`,
  `oil_unit_for_costing`, `oil_mass_grams_for_costing`, `units_produced`, `currency`), so
  an export needs no client-side state.
- `RecipeController::accessibleCurrentVersion()` (line 844) already resolves the
  work-in-progress draft version → exporting the draft without publishing is nearly free.
- `$workbench['recipe']['public_id']` is available in
  `recipe-workbench/header.blade.php:3` — that is where the workbench action bar goes.
- `tests/Feature/HttpSecurityHardeningTest.php:57-64` asserts `throttle:workspace-exports`
  on `recipes.export.xlsx`; new export/print routes must be added there.
- OpenSpout v4.32 is installed (transitively via Filament) and used by
  `RecipeWorkbookExporter` — no new dependency needed.

Assumptions adopted in the plan (all cheap to reverse): costing export follows the recipe
view gate; batch production record is print-only with no server-side PDF retention;
stock-count sheet is print-only with no re-import.

Main risk flagged: **filter parity** — the inventory/ingredient exports are only useful if
they honour on-screen filters, which may require extracting filter parsing out of the
Livewire components.

### Owner brought a competing proposal; I evaluated and merged

Owner pasted another agent's "follow the user's task on each view" proposal and asked for an
evaluation. Wrote
`docs/superpowers/plans/2026-09-28-export-print-approach-comparison.md`. Verdict: merge.
Still no code written.

**Adopted from theirs (they beat me on these):**
- *Never silently export older numbers* — workbench draft ≠ published version. I missed it.
- *Batch sheet (before/during) vs batch record (completed) are two artifacts*, not one.
  `ProductionRunStatus` enum exists (`ProductionDetail.php:27`) so the split is feasible.
- Export must span **all pages**, not just the current page.
- A completed **batch record must be immutable** — must not drift when today's formula or
  ingredient price changes. GMP correctness issue I missed.
- Drop my standalone "method card" — reuse the working formula document.
- "Ingredients to weigh" ≠ "calculated composition" — sharper naming than mine.
- Spreadsheet hygiene: numeric cells, separate units column, generation date.

**Rejected / adjusted:**
- Their "Print formula & procedure" is a **phantom artifact**: `recipes/print.blade.php`
  already renders the manufacturing procedure conditionally at lines 50-53, so their Formula
  and Instructions rows would produce one document under two labels — recreating the
  five-duplicate-print-routes bug.
- Their "Save formula and print" couples a mutation to a print action; this project has open
  autosave questions. Better: `accessibleCurrentVersion()` already resolves the draft, so
  export the draft directly and just *label* the source.
- Their INCI demotion is half right — verified `ingredient-list-preview.blade.php` has four
  copy buttons (generated INCI:56, final INCI:86, generated plain:125, final plain:154), so
  my Tier 1 → **Tier 2**. But keep a printable declaration for the PIF file.
- Selected-rows export = scope creep for v1. They were silent on throttling.

**Kept from mine (they missed):** the five duplicate print routes; the ingredient price
catalog (they never discussed the dashboard Ingredients list — it's the user's price book);
the feasibility grounding; runs vs batches distinction.
