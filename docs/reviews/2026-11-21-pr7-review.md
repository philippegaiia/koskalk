# Review: commit c155ca16 "Restore water costing and allow incomplete batch costs" (PR #7)

Scope: correctness only. Read-only review on 2026-11-21. I read the code paths and did not run the tests or query the database.

## Verdict

I found **no confirmed correctness bug** in the commit. The water resolver, the alkali and water rows in recipe-bench batches, the unpriced markers, and the views all behave as intended for the main cases. Three items are rated **plausible**: each needs particular data or a failed calculation to happen. Two notes on coverage and behaviour follow.

## What I checked and found correct

- **`CanonicalSoapWaterResolver`** (`app/Services/CanonicalSoapWaterResolver.php:24`) looks up CH2 first and falls back to category+subcategory. It accepts active platform rows only, with `withoutGlobalScopes()`, and all three former private lookups now use it.
- **Rule "Costing reads project defaults without writes"** (`.ai/rules/services.md:55`). `build()` calls only `projectCosting()`, which works in memory, then the read-only resolvers. The preview creates no costing rows; the existing test "records production snapshots with unpriced ingredient rows without creating costing" covers this.
- **Scaling to the batch basis.** Derived rows (`is_derived`) cost `weight × basis/batch_size` (`RecipeVersionCostPreviewBuilder.php:315-321`), the same path the costing tab uses through `buildFromCosting(includeDerivedRows: true)`. The default basis comes from `batch_mass_grams` or `batch_size`, so the ratio is 1 unless a basis is supplied.
- **Dual lye and KOH purity.** NaOH uses `naoh_weight` and KOH uses `koh_to_weigh` (the purity-adjusted weight, matching `RecipeCompositionExportDataBuilder:197`). The positions (NaOH 1, KOH 2; KOH-only 1) match `alkaliDesiredRows()` in the synchronizer, so the saved prices are found.
- **Missing alkali.** `alkaliDesiredRows()` calls `resolveMany()`, which throws, so `projectCosting()` fails before any row is built. The controller shows `calculation_error` and `record()` re-throws. A batch never records silently without lye because the alkali is missing from the catalog.
- **Liquid soap.** Dilution and neutralizer water are added through `addedDilutionWaterWeight()` only when `liquid_process.status === 'ok'`. Addition phases are resized as before.
- **Cosmetics.** `isSoapVersion()` returns false, so the snapshot is null and no synthetic rows are added.
- **Unpriced markers.** `has_unpriced_rows` is set from any row with a null price (`buildFromTransientRows` at `:270`). `sumKnownCosts` adds only non-null line costs. `price_per_kg` stays null for unpriced ingredients (the column is nullable). A typed 0 becomes `"0.0000"`, which is not null, so it shows as a real price. Packaging stores `is_unpriced`.
- **`total_cost` null.** `units_produced` is required (`StoreProductionBatchRequest:25`), and `legacyPreviewShape` turns a null packaging total into 0. The non-null columns are always filled.
- **Views.** `show.blade.php` (per-unit card, ingredient and packaging rows), `print.blade.php` (rows and cost summary) and `recipes/version.blade.php` (record-panel warning, history line) all label unpriced rows and incomplete totals. Batches recorded before this commit could not have unpriced rows, because the guard added in 560f64df dates from table creation. The `false` default is therefore correct for them.
- **Other readers of `production_batches` totals.** I grepped `app/`, `resources/views` and `routes`. Only the three views above read `total_cost`, `cost_per_unit` or `ingredient_total` from batches; `account/show.blade.php` reads only usage counts. No export reads batch totals.

## Plausible issues (unverified, ranked)

### 1. A soap batch can record without lye or water, and be marked complete, when the saved calculation is null (plausible)

- **Where:** `RecipeVersionCostPreviewBuilder.php:538` (`if (! $calculation ...) return [];`) and `:77-83`.
- **Scenario:** `versionSnapshot()` returns `calculation => null` for a saved soap version, for example a version whose oils no longer give a valid SAP result after a catalog change. `savedSyntheticRows()` then returns `[]`. The batch records with no NaOH/KOH or water rows, and `has_unpriced_rows` is false because nothing is unpriced. The batch shows a complete cost that leaves out the lye and the water.
- **Partly the same:** when `liquid_process.status !== 'ok'`, only the dilution water is dropped, also silently.
- **Why plausible:** `calculationFromWorkbenchDraft()` is typed `?array`, but I did not confirm that a saved soap version can actually reach null.
- **Suggested fix:** in `build()`, when the version is soap and the snapshot calculation is null (or the liquid process is not ok), raise a `ValidationException`. The controller already turns that into `calculation_error`. Alternatively, set an "incomplete" flag so the batch cannot read as complete.

### 2. Water missing from the catalog is dropped silently, not flagged (plausible, low)

- **Where:** `RecipeVersionCostPreviewBuilder.php:603-617`, and the synchronizer's `implicitWaterDesiredRows()` at `RecipeVersionCostingSynchronizer.php:786-790`.
- **Scenario:** no active platform row has CH2 or the water subcategory, which is the same kind of catalog drift that caused this bug. The water row then disappears from the costing tab and from the batch, and the batch cost reads as complete. Alkali fails loudly in this situation; water does not.
- **Suggested fix:** for soap versions with a positive water weight, treat an unresolved water ingredient like a missing alkali: throw, or add an unpriced placeholder row that sets `has_unpriced_rows`. At minimum, log it.

### 3. Saved water prices may be orphaned if the CH2 row differs from the row the old lookup chose (plausible, data-dependent)

- **Where:** `CanonicalSoapWaterResolver::resolve()`, used by `implicitWaterDesiredRows()`.
- **Scenario:** a catalog has two platform water rows: CH2 (id Y) and an older row with subcategory `water` (id X). The old lookup picked X, so the saved `implicit_water` costing items are keyed `X:implicit_water:1`. After this commit the desired row is `Y:implicit_water:1`, which takes the workspace default price or null. The saved price on X becomes a saved-only row that the batch preview ignores, so the water shows as unpriced or at a different price.
- **Production:** the old lookup found nothing there (the subcategory had drifted), so production is likely unaffected. Other environments could be affected.
- **Check:** `select id, catalog_key, subcategory from ingredients where owner_id is null and workspace_id is null and (catalog_key = 'CH2' or subcategory = 'water');` should return a single row.
- **Suggested fix if more than one row:** a one-off data fix, or migrate `implicit_water` costing items to the CH2 id.

## Notes (not bugs)

- **Most batches will now read "Cost incomplete" by default.** Every soap batch now has NaOH/KOH and water rows. Unless the workspace has priced those materials (a `CurrentMaterialPrice` or a saved costing price), the batch is marked incomplete. This follows the decision that a missing price is not a 0. Users who never priced water will see the marker on almost every batch, so the UX may need a hint like "price water at 0 if it is free".
- **Test coverage gap.** The new batch test covers only bar soap with NaOH. Recording a batch is not tested for KOH-only (purity), dual lye, liquid soap (dilution water), or a cosmetic formula (no synthetic rows). The code paths are shared with the costing tab, which has tests in `RecipeWorkbenchCostingAlkaliTest`, but the batch scaling through `build()` is not covered for those cases.
