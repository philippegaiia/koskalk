# Production Bench Supplier UX Correction

## Scope

This correction applies to the Suppliers and Supplier listings checkpoint of the
Production Bench purchasing redesign. It supersedes the copy and form placement
implemented through commit `a4d8afd`. It does not change listing calculations,
workspace isolation, entitlement behavior, or the later quotation, purchase-order,
receipt, and inventory designs.

## Product Voice

The authenticated Production Bench is an operational tool for users who already
understand their work and have already purchased access. Its copy must not promote
Soapkraft or explain obvious purchasing concepts.

Every page should use:

- a factual page title;
- field and table labels;
- short state messages;
- contextual help only where a field or calculation can reasonably be
  misunderstood.

The pages must remove:

- promotional or benefit-led introductions;
- headings followed by paragraphs that restate the heading;
- instructions that tell an experienced maker why suppliers or listings matter;
- placeholders for functionality that does not yet exist;
- phrases such as “manage suppliers,” “the supplier you buy from,” and “coming
  later” where a label, count, or neutral empty state is sufficient.

Neutral examples:

- `Suppliers`
- `No suppliers.`
- `Supplier listings`
- `No supplier listings.`
- `Read-only. Resume Production Bench to make changes.`

Short technical help remains appropriate for pricing basis, unit conversion, and
the relationship between a supplier listing and an existing Soapkraft ingredient.

## Supplier Identifier

Every supplier retains its automatically generated UUID `public_id`. The UUID is
the stable system and URL identifier and is not shown as the supplier's operational
code.

Every supplier also has a required human-readable `code`:

- entered by the user;
- required on create and update;
- unique within the workspace, compared case-insensitively;
- maximum 16 characters;
- trimmed and stored in uppercase;
- accepts letters, numbers, hyphens, and underscores;
- may follow any customer-defined coding system;
- is never silently generated by Soapkraft.

Examples include `OLVEA`, `AMAZON`, `SUP-004`, and `OIL_FR_01`.

The code appears in supplier lists, supplier details, search results, purchase
documents, and future supplier selectors. Renaming a supplier does not change its
code. Changing the code is permitted but must preserve workspace uniqueness.

Existing development suppliers receive a deterministic migration backfill. The
backfill uses `SUP-<id>` truncated to the permitted length and resolves collisions.
After backfill, the database column becomes non-null and has a workspace/code
unique index. New records never rely on this fallback.

## Information Architecture

### Suppliers Index

The Suppliers index contains:

- title `Suppliers`;
- primary action `Add supplier`;
- search, state, sorting, and bounded pagination;
- supplier rows showing code, name, location, main contact, state, and listing
  count.

It does not contain the supplier creation form. Its empty state is simply `No
suppliers.` with the Add supplier action remaining visible.

### New Supplier Page

`Add supplier` opens a dedicated `New supplier` page.

The form is divided into ordinary field groups rather than one large undifferentiated
grid:

1. **Supplier**: required code, required name, active state, default currency.
2. **Main contact**: name, email, telephone, website.
3. **Address**: address lines, city, region, postal code, country.
4. **Notes**: optional notes.

The only primary action is `Save supplier`. Cancel returns to Suppliers. Successful
creation opens the supplier detail page.

### Supplier Detail

Supplier detail shows the supplier code alongside the name and keeps supplier
editing separate from listing creation.

The page contains:

- factual identity, contact, address, state, and notes;
- an `Edit supplier` action;
- a Supplier listings section with an `Add listing` action;
- the current listing table and its filters.

The existing large edit form and embedded listing-creation form are removed. The
quotation, purchase-order, and receipt placeholder cards are removed until those
features exist.

### Edit Supplier Page

`Edit supplier` opens a focused form using the same grouping and validation as New
supplier. Save returns to supplier detail.

## Supplier Listing Creation

### Discoverability

Users can start a listing from either:

- `Add listing` on the Supplier listings index; or
- `Add listing` on supplier detail.

Both actions open the same dedicated `New supplier listing` page.

When launched from supplier detail, the supplier is preselected and displayed as
read-only context. When launched from the global index, Supplier is the first
required field. The page must not create a supplier or ingredient inline.

### Form

The listing page contains only listing fields:

1. Supplier.
2. Existing ingredient or packaging item.
3. Supplier SKU and supplier-facing item name.
4. Purchase format, net quantity, and unit of measure.
5. Pricing basis, amount, applicable price unit, and calculated counterpart.
6. Minimum order, active state, and notes.

The calculation preview remains because it clarifies whether the entered value is
per unit or the total purchase-format price. It uses exact decimal strings and the
workspace's kg/lb basis.

Successful creation returns to supplier detail when the supplier was preselected;
otherwise it returns to the Supplier listings index. Cancel returns without saving.

## Validation and Error Handling

- Supplier code errors attach to the Code field.
- A duplicate code identifies that the code is already used in this workspace.
- Missing supplier, material, purchase format, quantity, or price remains on the
  listing form with field-level errors.
- Cross-workspace supplier and material IDs are rejected server-side.
- Cancelled Production Bench workspaces can view existing records but cannot open
  or submit creation/edit forms.
- UUIDs, database IDs, and canonical gram values are not exposed as customer input.

## Testing

Tests must prove:

- supplier code migration backfill, non-null constraint, 16-character limit, and
  case-insensitive workspace uniqueness;
- the same code may be used in different workspaces;
- New supplier creates all structured fields and redirects to detail;
- Edit supplier updates the code and fields without changing `public_id`;
- Suppliers index contains no creation form or promotional copy;
- supplier detail contains clear Add listing and Edit supplier actions but no
  embedded creation/edit forms or future-feature placeholders;
- global Add listing requires a supplier;
- supplier-detail Add listing preselects and locks the supplier context;
- listing creation retains existing price, tenancy, unit, pagination, localization,
  read-only, and precision behavior;
- all new routes require authentication and Production Bench access;
- copy regression assertions reject the removed promotional phrases.

## Acceptance Criteria

The correction is complete when a user can immediately identify where to add a
supplier or listing, each creation task has its own focused page, supplier code is
required and unambiguous, and the interface reads like operational software rather
than a product sales page.
